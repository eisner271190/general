# Question 002

- [x] [researcher] ¿La API key del proveedor de IA va como clave nueva en el secreto existente (`openrouter-api-key`) o se reutiliza la clave `api-key` que `cloud/up.ps1` ya siembra?
  - Contexto: el secreto es único por aplicación (`generator/components/cloud/aws/templates/terraform-secrets-manager.scriban:6-16`) y `up.ps1` siembra claves fijas: `@('jwt-secret','api-key','subscription-secret-key','subscription-webhook-secret')` en `generator/components/cloud/aws/templates/up.ps1.scriban:290`, con valor por defecto `PLACEHOLDER_CAMBIAR_EN_AWS` en `up.ps1.scriban:272-274`. Spring Cloud AWS expone cada clave JSON del secreto como propiedad (`application-cloud-properties.scriban:1` importa `aws-secretsmanager:{{ ENVIRONMENT }}/{{ APPLICATION_ID }}`).
  - Tarea: 001
  - Solución propuesta: añadir clave `openrouter-api-key` a `$seededKeys` (`up.ps1.scriban:290`) con valor por defecto `OPENROUTER_API_KEY_PLACEHOLDER` (`up.ps1.scriban:265-285`) y leerla en el backend como `${OPENROUTER_API_KEY:${openrouter-api-key:}}`. Evita colisión semántica con `api-key` (hoy sin uso en el backend: no aparece en `application-properties.scriban:44-48`).
  - Respuesta (2026-10-01, architect): clave nueva, pero **`ai-api-key`** (no `openrouter-api-key`). El objetivo es agnosticismo: nombrar la clave con el proveedor la ata a OpenRouter. `ai-api-key` casa con las propiedades `ai.*` y con la variable de entorno `AI_API_KEY` en local. Leerla como `ai.api-key=${AI_API_KEY:${ai-api-key:}}`; default en `up.ps1` = `AI_API_KEY_PLACEHOLDER`. No se reutiliza `api-key`. Ver `architecture-001.md` §5.1 y §12.
